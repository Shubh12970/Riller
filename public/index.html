A single request passes while its bucket still has tokens - once the bucket is empty, even one request gets a 429. A burst spends the saved-up tokens. A flood shows the steady-state rate: a wall of 429s with only the refill rate getting through.

Concurrency proof

One click fires 20 parallel requests at a fresh throwaway key whose bucket holds 10 tokens. If the shared store is atomic, exactly 10 are allowed - no two requests can spend the same token. This demonstrates the guarantee on a bounded run; it is a test you can rerun, not a claim you have to take on faith. The endpoint is itself rate-limited (10 runs/min per visitor) and never touches a real caller's bucket.

Demo limits, on purpose

This is a public demo, so it defends itself. The buttons fire at most 150 requests, in batches of 10 so one click never opens hundreds of connections. The server keeps at most 10,000 buckets per route and forgets keys idle for 10 minutes; the chart keeps only the last two minutes. Bucket state and this chart are shared across all of Cloudflare's copies of this worker through a Durable Object, so the limits hold globally - running locally with npm run dev uses per-process memory instead.
