4. How the system works

The request flow, end to end:

  • A request arrives at the Express server (for example POST /api/login).
  • Before any route logic runs, it passes through the rate-limit middleware. "Middleware" just means code that runs in the middle, before the handler.
  • The middleware decides WHO is calling - the key. Reads are keyed by IP address; login is keyed by IP plus username (an attacker guessing passwords has no account yet, so keying by user id would not slow them); the heavy route is keyed by API key.
  • The middleware asks the token bucket: does this key have a token? Locally the bucket lives in memory; on the live deployment the middleware asks the Durable Object, which runs the exact same decision math against the shared buckets. The bucket refills at a steady rate; each request spends one token.
  • Allowed: the request continues to the real route handler, with X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset headers attached so honest clients can pace themselves.
  • Rejected: the middleware answers 429 immediately with a Retry-After header and a small JSON body. The route handler never runs, the database is never touched - the flood stops at the gate.
  • Every decision is recorded by the stats recorder, and the dashboard page polls it once a second to draw the live allowed-vs-rejected chart.

5. The three algorithms, and why token bucket won

Fixed window (src/core/fixedWindow.ts) counts requests per clock minute. Simple, but a burst at 10:00:59 and another at 10:01:00 fall in different windows, so twice the limit passes in two seconds. One of the tests proves this with 120 requests accepted under a 60/minute limit. It stays in the project as the baseline to compare against - being able to show its weakness with a test is exactly what an interviewer wants to hear.

Sliding window log (src/core/slidingWindow.ts) remembers the timestamp of every recent request and counts them. Accurate, no edge bursts - but memory grows with traffic per caller. Fine at small scale, expensive at large scale.

Token bucket (src/core/tokenBucket.ts) gives each caller a bucket holding up to N tokens, refilling at a steady rate. Each request spends one token; empty means wait. It allows short bursts while capping the long-term average, uses two numbers of memory per caller, and handles bursts and steady rate with a single mechanism. This is what protects the demo routes. The decision math is one pure function (consumeToken), so the local limiter and the Durable Object run identical, test-covered code.

Two details worth noticing in the code: the clock is injected as a parameter, so tests can simulate minutes passing in milliseconds; and a backwards clock jump (a server time correction) is clamped to zero elapsed, so a backwards jump drains no earned tokens; a forward jump adds some, but only up to the capacity lid. Both are test-covered.

6. Known limits, honestly

  • Local in-memory state forgets everything on restart and is invisible to other processes - which is why the deployed worker uses the shared store. The shared store routes every decision through one named Durable Object: that is what makes each check-and-spend atomic, but it also makes the object the single decision point - the same shape of tradeoff as a single Redis primary. High-traffic systems shard by key; for this project one object is right.
  • Keying by IP is imperfect: many users share a NAT/campus IP, and attackers rotate IPs. Real systems layer keys (IP + account + API key), which the middleware supports through its keyGenerator.
  • The dashboard stats live in memory too and reset on restart - it is a teaching instrument, not monitoring.
  • Everything is bounded so the public demo cannot eat itself: at most 10,000 buckets per store, idle keys evicted after 10 minutes, the chart keeps two minutes, and demo buttons fire at most 150 requests in batches of 10.

11. The web basics every piece stands on

Before any code, six ideas. Every later section uses them.

11.1 What a server and a client are

A server is a program running on a computer that waits for other programs to ask it for things. A client is the program that asks. Your browser is a client. In this project, the server is a small program we wrote, and the clients are your browser and a command-line tool called curl (explained in 21.6). When you open the demo page, your browser asks our server for the page; when you click a fire button, your browser asks our server for data.

11.2 What an API is

An API (application programming interface) is the set of questions a server agrees to answer, and the shape of the answers. This project's demo API agrees to answer three questions: GET /api/data (give me some data), POST /api/login (check a login), GET /api/heavy (do something expensive). Each question is called an endpoint or a route. The rate limiter exists to control how often any one client may ask.

11.3 Requests and responses

Every API conversation is one request and one response. A request has four parts: a method (what kind of asking: GET means 'read something', POST means 'send something'), a path (which endpoint, like /api/login), headers (small labelled notes about the request, like x-api-key: demo-key-1), and sometimes a body (the actual content sent, like the username and password). A response has a status code (a number that says how it went), headers, and a body.

Status codes you will see in this project: 200 means OK, 400 means 'your request was malformed', 401 means 'not logged in / wrong credentials', 404 means 'no such thing', 429 means 'too many requests - slow down', 500 means 'the server itself failed'. The rate limiter's whole job is to answer 429 at the right moments.

11.4 JSON

JSON (JavaScript Object Notation) is the text format the bodies use. It looks like this: {"username": "demo-user", "password": "wrong-on-purpose"}. It is just labelled values written as text: names in quotes, a colon, then the value. Servers like ours read it with JSON.parse and write it with JSON.stringify.

11.5 Why rate limits exist at all

Three reasons, and the demo has one route for each. First, protection: a server has limited capacity, so no single client should be able to use all of it (the /api/data route). Second, security: a login endpoint without a limit lets an attacker try millions of passwords (the /api/login route). Third, fairness: if customers share an API, one noisy customer must not starve the others (the /api/heavy route). When an interviewer asks 'design a rate limiter', these three are the needs hiding inside the question.

12.1 The terminal

The terminal is the text window where you type commands to the computer instead of clicking. Every command in this document (npm install, npm test, curl ...) is typed there. When this document says 'run X', it means: open a terminal in the project folder, type X, press Enter.

Node.js is a program that runs JavaScript outside a browser. JavaScript was born inside browsers; Node lets the same language power servers. You check it is installed by running node --version. 12.3 npm and package.json

npm is Node's package manager: it downloads packages (reusable code other people wrote) and records what your project needs. The record is the file package.json. Its important fields in this project: name (the project's name), type: "module" (which import syntax the files use - modern import/export, not the older require), scripts (named commands you can run: npm run dev starts the demo, npm test runs the tests), dependencies (packages the server needs to run - just Express), devDependencies (packages only needed while developing: the test runner, TypeScript tooling). The file package-lock.json records the exact versions downloaded, so everyone gets identical code.

12.4 TypeScript

TypeScript is JavaScript plus labels that say what kind of thing each value is. In plain JavaScript, consume(key) accepts anything; in TypeScript, consume(key: string) says key must be text, and the computer warns you BEFORE running if you pass a number. Those labels are called types. Files end in .ts. One more piece of syntax you will see constantly: an interface is a named shape for an object. When the code says interface BucketState { tokens: number; lastRefillMs: number }, it means 'any BucketState is an object with at least these two fields, both numbers'. TypeScript matches shapes, not exact contents: an object with EXTRA fields still counts as a BucketState (this is called structural typing). One seeming exception: when you build an object literally on the spot, TypeScript also warns about extra fields it did not expect (the excess-property check) - a typo-catcher, not a contradiction of structural typing. Types disappear when the code runs - they exist only to catch mistakes early and to document shapes.

12.5 tsx

Older Node versions cannot run .ts files directly - something must strip the types first. (Since Node 22.18, Node can erase simple type annotations itself and run .ts files natively; this project still uses tsx so the same commands work across Node versions and reload-on-edit comes free.) tsx does that on the fly, so npm run dev 'just works' and reloads when you edit a file. You never call tsx yourself; the scripts call it.

14. Step 2: the token bucket - the heart of the project

14.1 The idea in plain words

Give every caller an imaginary bucket. The bucket holds up to N tokens (N is the capacity - the biggest burst allowed). Tokens drip in at a steady speed (the refill rate). Every request spends one token. An empty bucket means 'wait'. That is the entire algorithm; everything else is arithmetic. Example with capacity 5 and refill 1 per second: a caller who has been away for a while has a full bucket and can fire 5 requests instantly (the burst); after that, sustained use averages 1 request per second. 'Averaging' is the honest word: whenever the caller pauses, tokens drip back in, and after about 5 quiet seconds the bucket is full again and another instant 5-burst is possible. The limiter controls the long-run rate and the biggest burst; it does not force traffic to arrive evenly.

14.2 The two numbers we remember per caller

We do NOT store every request. We store two numbers per caller: tokens (how full the bucket is, a decimal like 3.5) and lastRefillMs (when we last updated that number). lastRefillMs is a timestamp: the number of milliseconds since 1 January 1970, which is how computers write down a moment in time. Date.now() gives the current one.

14.3 The math

When a request arrives: work out how many seconds passed since lastRefillMs (call it elapsed). Add elapsed x refill rate to the bucket, but never above capacity. If the bucket now holds at least 1 token, spend one and allow the request. Otherwise reject it, and compute how long until one token exists - that waiting time becomes the Retry-After header from 11.3. Two safety details: if the computer's clock jumps backwards (small corrections from network time sync are normal), elapsed would go negative, and a negative elapsed x rate would DRAIN tokens the caller honestly earned - so elapsed is clamped at zero with Math.max, and a backwards jump simply means 'no refill this check'. A forward jump adds tokens instead, but the capacity lid bounds that too. The second detail: the reset-time header is computed AFTER the spend, not before - getting that order wrong was the one real bug the tests caught (section 19).

14.4 The code, walked line by line

Here is the actual decision, from src/core/tokenBucket.ts, with every line explained: 

const elapsedSeconds = Math.max(0, (nowMs - state.lastRefillMs) / 1000);
const tokens = Math.min(capacity, state.tokens + elapsedSeconds * refillPerSecond);
if (tokens >= 1) {
  const afterSpend = tokens - 1;
  return { state: { tokens: afterSpend, lastRefillMs: nowMs }, result: { allowed: true, ... } };
}
return { state: { tokens, lastRefillMs: nowMs }, result: { allowed: false, ... } };
  • Line 1: nowMs minus lastRefillMs is milliseconds passed; divide by 1000 for seconds. Math.max(0, ...) is the backwards-clock clamp from 14.3.
  • Line 2: refill math. state.tokens + elapsedSeconds x refillPerSecond is 'old tokens plus what dripped in'. Math.min(capacity, ...) is the bucket's lid.
  • Lines 3-5: the allow branch. afterSpend is the new bucket level. The function returns two things: the new state to store, and the decision ({ allowed: true, limit, remaining, retryAfterSeconds, resetSeconds } - the exact fields the middleware turns into headers).
  • Line 7: the reject branch. The bucket keeps its fractional tokens (0.4 stays 0.4 - that fraction is how 'wait 0.6 seconds' is possible), and the decision says allowed: false plus how long to wait.

New syntax used here: const declares a value that will not be reassigned; Math.max/Math.min pick the larger/smaller of two numbers; the { ... } braces group statements and also build objects; return hands a value back to whoever called the function. The '...' above stands for header fields omitted here for readability - the real file has them written out. Every code block in this document is a teaching excerpt like this one: real lines from the named file, with repetitive parts sometimes left out. The runnable source of truth is always the file itself.

14.5 The class that wraps it

consumeToken is a pure function: same inputs, same outputs, no memory of its own. The project wraps it in a class (TokenBucketLimiter) - a template for making limiter objects. A class bundles data (capacity, refill rate, the store, the clock) with the function that uses them. constructor is the function that runs when you make one: new TokenBucketLimiter({ capacity: 30, refillPerSecond: 10, store }). Inside, this means 'this specific limiter object', so this.capacity is that object's capacity. The keyword async on consume means the function returns a Promise: a 'value that will exist shortly'. Callers write await limiter.consume(key) to get the real result. Why Promise at all? Because some stores answer over a network hop (section 21) - an interface that must be instant cannot allow that, so the interface promises instead. Section 17 goes deeper.

14.6 What you should see

15. Step 3: remembering who called - the store

The bucket math needs somewhere to keep 'the two numbers' per caller between requests. Locally that place is MemoryStore (src/core/memoryStore.ts): a Map, which is JavaScript's built-in dictionary. A Map stores key -> value pairs (here: caller key -> BucketState) with map.get(key), map.set(key, value), and map.size. Its defining strength: get and set take roughly the same tiny time on average, no matter how many keys exist - you will hear this called 'average O(1)'. The honest caveat: rare worst cases (too many keys landing in the same internal slot, or the table pausing to resize as it grows) take longer. Engineers quote the average because worst cases are rare and the average is what a running system actually feels.

Two design decisions live here. First, the store is hidden behind an interface (TokenBucketStore) so the limiter does not care WHERE state lives - memory locally, a Durable Object deployed (section 21). That is the swap-ability the interview answer leans on. Second, the Map is not allowed to grow forever: it is capped at 10,000 keys, keys idle for 10 minutes are evicted, and if it still overflows, the least-recently-touched keys go first. A public demo MUST do this, otherwise a flood of made-up caller keys (random IPs, random usernames) would grow memory until the server fell over. You will see this bounding theme again in the dashboard buttons and the JSON body cap - a public demo defends itself everywhere, not just at the rate limit.

16. Step 4: the other two algorithms (and the tradeoffs each makes)

Fixed window (src/core/fixedWindow.ts): count requests per clock minute; when the count passes the limit, reject until the next minute starts. One counter per window makes it the cheapest limiter here, and gives it a known edge case: a burst at 10:00:59 and another at 10:01:00 are in DIFFERENT windows, so twice the limit can pass in two seconds. The test suite proves this on purpose: 120 requests accepted under a 60-per-minute limit. Whether that edge case matters depends on the job: for coarse, forgiving quotas (a free tier's daily cap, an internal tool), the simplicity is worth it and teams choose fixed window on purpose. For this demo - where a visible double-burst would undercut the lesson - it loses.

Sliding window log (src/core/slidingWindow.ts): remember the timestamp of every request and count how many fall in the last 60 seconds. Accurate, no edge bursts - the cost is memory: every timestamp is stored, so memory grows with traffic, which is exactly what token bucket avoids with its two numbers. When traffic is modest, or precision matters more than memory (audit-grade fairness, small customer counts), the log is a legitimate choice. For this project's demo scale and interview story, the bucket's constant memory wins.

Keeping both in the repo is deliberate: being able to show the tradeoffs of each, pinned down by tests, is worth more in an interview than the winner alone.

17. Step 5: the middleware - where algorithms meet the web

17.1 What middleware is

Express is the web framework: it listens for requests, matches them to routes, and runs our code. Its central idea is middleware: functions that run in the middle, before the route's own handler. A request flows through them in order: jsonBody() (reads the body) -> rateLimit(...) (the limiter) -> the route handler (the actual answer). Any of them can end the request early - the limiter ends it with 429 when the bucket is empty, so the route handler never runs. 'The flood stops at the gate' is this sentence.

17.2 The code, walked line by line 

const key = keyGenerator(req);
const result = await options.limiter.consume(key);
res.setHeader('X-RateLimit-Limit', result.limit);
res.setHeader('X-RateLimit-Remaining', result.remaining);
res.setHeader('X-RateLimit-Reset', result.resetSeconds);
if (!result.allowed) {
  res.setHeader('Retry-After', result.retryAfterSeconds);
  res.status(429).json({ error: 'Too many requests', retry_after_seconds: result.retryAfterSeconds });
  return;
}
next();
  • req is the incoming request object; res is the response being built; next() means 'pass to the next middleware'.
  • Line 1: decide WHO is calling. keyGenerator is a function passed in as a setting - functions can be stored and passed like any other value in JavaScript. Default: the caller's IP address (their network identity). The login route passes its own: IP plus username (17.4 explains why).
  • Line 2: ask the limiter. await pauses this function until the Promise from 14.5 resolves - meanwhile the server handles other requests; awaiting does not freeze the whole server.
  • Lines 3-5: attach the three X-RateLimit headers to EVERY response, allowed or not, so honest clients can pace themselves.
  • Lines 6-10: the reject branch: Retry-After header, status 429, a small JSON body, and return - next() is never called, so the route handler never runs.
  • Line 11: the allow branch: next() hands the request on.

This too is a teaching excerpt. The runnable file (src/middleware/rateLimit.ts) wraps these lines in the exported shell - export function rateLimit(options) { return async (req, res, next) => { ... } } - plus a try/catch that forwards store failures as a 500 instead of hanging (17.3). The shell means: calling rateLimit({...}) builds a middleware function customized by your options, ready to plug into a route.

17.3 Why the limiter call needs await

Locally, consume reads a Map - instant. Deployed, it asks a Durable Object over Cloudflare's internal network - not instant. One honest interface covers both: consume returns a Promise, the middleware awaits it. If the store itself fails, the try/catch around the middleware body passes the error to Express with next(err), which answers 500 instead of hanging silently. Failing loudly is a feature.

17.4 Choosing the key is the real design work

The algorithm is settled; WHO to limit is the interview question. Reads key by IP (the caller's network address). Login keys by IP + username: an attacker guessing passwords has no account yet, so keying by account id would not slow them; keying by IP + username also stops one attacker from spraying many usernames from one IP... it actually stops them per-username - and a single determined account gets its own small bucket. The heavy route keys by API key (a password-like string customers send in the x-api-key header), because fairness is per customer, not per machine. One caution documented in the code: many real users can share one IP (a campus, an office), so IP keys are a blunt instrument - layered keys are the grown-up version.

18. Step 6: the demo API - three routes, three lessons

The demo exists so every concept has buttons attached. Its routes, and the lesson each one teaches:

  • GET /api/data - loose read limit (30 burst, refills 10/sec, keyed by IP). Lesson: limits are per-route policy, not one global switch.
  • POST /api/login - strict on purpose (5/minute per IP + username). Lesson: brute-force math. At 5 tries per minute, one attacker gets 300 guesses per hour, about 7,200 per day; an 8-character password has roughly 200,000,000,000,000 combinations. Without a limit, guessing is a laptop's afternoon; with it, guessing is hopeless. The route always answers 401 - it is a demo with nothing to log into - which also shows the limiter rejects BEFORE credentials are even checked.
  • GET /api/heavy - per-API-key (10/minute). Lesson: fairness; one noisy customer cannot starve others because each key gets its own bucket.

One engineering story lives in this file. Express's built-in JSON reader (express.json()) pulls in a chain of packages ending in one called iconv-lite, which converts between text encodings using a trick the Workers runtime does not support - so on Cloudflare, express.json() crashes the request. The fix is twenty lines: a small jsonBody() that reads the request text, parses it as UTF-8 JSON (the only encoding this API accepts), answers 400 on malformed JSON, and refuses bodies over 1 MB (the self-defending bound from section 15, applied to request sizes). Tradeoff stated in the code: no other charsets, fixed size cap. For this API, both are correct.

19. Step 7: the tests - how we know any of this works

A test is code that checks code. The project's 35 tests live in test/ and read like tiny scripts: arrange a limiter with a fake clock, act on it, assert what happened. 21. Step 9: putting it on the internet - Workers and the shared store

21.1 What serverless means

Running the demo on your own laptop only shows it to you. Serverless hosting (here: Cloudflare Workers) means: give the company your code; they run it on their computers, close to each visitor, starting it fresh when requests arrive and stopping it when idle. No server to rent, no card needed on the free tier - which the project's rules require.

21.2 wrangler and wrangler.jsonc

wrangler is Cloudflare's command-line tool: npx wrangler deploy uploads the code and makes it live. Its settings file, wrangler.jsonc, is worth reading line by line: name (the worker's name, which becomes its URL), main (the entry file, src/worker.ts), compatibility_date (which version of the Workers runtime behaviors to use), compatibility_flags nodejs_compat (speak enough Node to run Express), assets (serve the dashboard files directly), and the durable_objects + migrations blocks (section 21.4).

21.3 The bridge: how Express runs where there is no Node server

A Worker is not a Node server; it answers fetch events. A Cloudflare-provided bridge (httpServerHandler) wraps our Express app so each incoming fetch is translated into the request/response objects Express understands. The same app code runs locally on Node and deployed on Workers - one of the project's design rules ('the core knows nothing about HTTP') is what makes this possible at all.

21.4 The problem: many copies, one limiter

Cloudflare runs several copies (isolates) of a worker at once, each with its own memory. The first deployed version kept buckets in memory, so each copy enforced only its share of the traffic - two copies, each allowing the full limit. The fix is a Durable Object: a named object that exists once, that every isolate can call, and that handles one call at a time. 'One at a time' is what makes each check-and-spend atomic: two isolates can never both spend the last token, which a get-then-set split across two calls could not guarantee. The object's storage also persists the buckets and the stats feed, so restarts forget nothing.

The honest tradeoff, also in the docs' known-limits: one named object is one decision point - the same shape of tradeoff as a single Redis primary on self-hosted servers. Right for this project; high-traffic systems shard by key instead.

21.5 The bug only the real runtime could teach

The first shared-store version passed all local tests, deployed, then answered 500 on every second request. The reason: Cloudflare binds I/O objects (like the Durable Object stub) to the request that created them - a cached pipeline was answering later requests with a dead stub. The fix is to build the Express pipeline per request (a few cheap registrations). The lesson is written in src/worker.ts and repeated here on purpose: some constraints only appear in the real environment, which is why 'it passed the tests' is never the last step - verifying the live system is.

21.6 curl: checking the deployment from the terminal

curl sends requests from the terminal - the same conversations the browser has, but typed. curl -i https://api-rate-limiter.2wf0w2.workers.dev/api/data shows the response WITH headers: you should see HTTP/2 200 and the three X-RateLimit headers. 23. Mistakes to watch for (learned the hard way in this build)

  • Computing reset before the spend instead of after - the bug the tests caught. Order matters when a value depends on a change you are making.
  • Forgetting await on a Promise: you get a Promise object where you expected a result, and the error appears somewhere unrelated. If a value looks like 'Promise { <pending> }', an await is missing.
  • Letting a Map grow without a cap: fine in a toy, fatal on a public server. Every unbounded collection in a public system is a future outage.
  • Trusting client-sent headers for identity without thinking: keys like x-api-key are claims, not proof; fine for fairness buckets, never for security decisions on their own.
  • Assuming 'passed the tests' means 'works deployed': the stub-lifetime bug (21.5) passed every local test. Verify the live system too.
  • Claiming absolutes in docs: 'always passes', 'private', 'unlimited'. This project's own documentation was corrected on exactly this - precise claims survive review; absolute ones do not.

Two details worth understanding. get returns BucketState | undefined - the | reads 'or': the answer is a BucketState OR undefined (Map's way of saying 'not here'), and the compiler makes callers handle both.     method: 'POST',

    throw new Error(`Shared rate-limit store answered ${res.status}`);

  return (await res.json()) as RateLimitResult;
}
  • this.stub is the handle to the Durable Object; stub.fetch(...) is Cloudflare's internal call - not the public internet, worker-to-object inside the platform.

  • throw new Error(...) is how code says 'something failed, stop here' - the try/catch in the middleware (17.3) catches exactly this and answers 500.

28.1 fixedWindow.ts - one counter, as code 

const windowStartMs = Math.floor(now / this.windowMs) * this.windowMs;
let state = this.windows.get(key);
if (!state || state.windowStartMs !== windowStartMs) {
  state = { count: 0, windowStartMs };
  this.windows.set(key, state);
}
if (state.count < this.limit) {
  state.count += 1;
  return { allowed: true, /* ...remaining fields... */ };
}
  • Line 1 finds which window 'now' falls in: divide by the window length, Math.floor rounds down to a whole window, multiply back to milliseconds. Every time between 10:00:00 and 10:00:59 maps to the same windowStartMs - that is the whole trick, and also the source of the edge burst: the window boundary is a hard cliff.
  • !state || ... - the exclamation mark is logical NOT ('if there is no state'), and || is OR: start a fresh counter when this caller has none OR their counter belongs to an older window.
  • { count: 0, windowStartMs } - an object literal using the shorthand: writing just windowStartMs means windowStartMs: windowStartMs.
  • state.count += 1 is compound assignment: 'count = count + 1'. The decision is one comparison - that is why this limiter is the cheapest of the three.

Try it: the fake clock's default start is 0 - exactly on a window boundary, which is what makes these numbers line up. With limit 2 and windowSeconds 60: consume twice, advance 59 seconds, consume - predict: rejected (same window). Advance 1 more second (t=60, the next window), consume - predict: allowed. Now start the clock at 7_000 instead and redo the arithmetic: windows still break at absolute t=60, t=120, ..., so the reset comes after advancing 53 seconds, not 60. The test in 28.4 starts at 59_900 for exactly this reason - it places the burst at a window's end on purpose.

28.2 slidingWindow.ts - a memory of every request, as code 

const cutoff = now - this.windowMs;
const log = (this.logs.get(key) ?? []).filter((t) => t > cutoff);
if (log.length < this.limit) {
  log.push(now);
  this.logs.set(key, log);
  const oldestRelevant = log.length > 1 ? log[0] : now;
  // ...build the allowed decision with resetSeconds from oldestRelevant...
}
  • cutoff is 'the oldest timestamp still inside the window'. Anything older stops counting.
  • filter is an array method: it builds a new array keeping only the items where the little arrow function answers true. Here: keep only timestamps newer than the cutoff. This one line is the sliding window - expired requests literally drop out of memory, which is why there is no edge burst.
  • push appends to the end of an array. The log stays oldest-first, so log[0] is always the oldest surviving request - and 'when does this window loosen?' is 'when log[0] falls out', which is what resetSeconds computes.
  • The ternary log.length > 1 ? log[0] : now reads: if more than one request survives, the oldest is the front of the log; otherwise (the one we just added) use now.
  • The cost is visible in the type: Map<string, number[]> - an ARRAY per caller, growing with their traffic. Compare BucketState's two numbers (14.2). Same job, opposite memory shape - section 16's tradeoff, now in types you can point at.

Try it: limit 3, window 10 seconds. Fire 3 requests, advance 5 seconds, fire 1 more (rejected). Predict Retry-After: about 5 seconds - when the FIRST request ages out. Advance 5, fire again: allowed. Token bucket would have answered differently (its tokens drip continuously) - run both and compare; that difference is the interview answer made physical.

29. Feature upgrade 1: tiered plans (free and pro API keys)

What it is, in plain words: until now the limiter treated every caller the same. Real APIs do not - a weather API sells a free tier and a paid tier, and the paid tier gets a bigger allowance. This upgrade makes the limiter multi-tenant: one limiter, several customers, each with their own limit. A "plan" is just two numbers (burst size and refill rate) with a name, and an API key says which plan a caller is on.

Why this is more than a basic limiter: a single-bucket counter limits traffic; a tiered system runs a pricing model. Limits stop being one global constant and become per-customer policy, which is what "API product" actually means. The demo proves it visibly: the free key exhausts at 10 requests per minute while the pro key still has 90 of its 100 left, and one tenant burning their budget never touches another tenant's.

The mechanism, walked through. The plans registry is plain data (src/core/plans.ts): 

export const PLANS: Record<string, Plan> = {
  free: { name: 'free', capacity: 10, refillPerSecond: 10 / 60 },
  pro:  { name: 'pro',  capacity: 100, refillPerSecond: 100 / 60 },
};
export function planForApiKey(apiKey: string | undefined): Plan {
  const planName = (apiKey && DEMO_API_KEYS[apiKey]) || 'free';
  return PLANS[planName];
}

Unknown keys fall through to the free plan - the same choice freemium APIs make when they allow keyless trial access. The demo keys (demo-free-key, demo-pro-key) are PUBLIC DEMO CREDENTIALS, not secrets: they exist so anyone can try both plans against the live demo. A production system would issue keys per customer and store only their hashes; shipping keys in source is fine here precisely because they protect nothing valuable.

The route (src/demo/server.ts, /api/ledger) builds one limiter per plan and picks between them per request - the middleware's limiter option became a function for exactly this. Buckets stay isolated because the shared store keys them by limiter id + caller key: ledger:free:demo-free-key and ledger:pro:demo-pro-key never overlap. A 429 names the caller's plan and how to get a higher limit: 

app.get('/api/ledger', rateLimit({
  limiter: (req) => planLimiters[planOf(req).name],
  keyGenerator: (req) => req.header('x-api-key') ?? req.ip ?? 'unknown-ip',
  rejectedExtra: (req) => ({
    plan: plan.name,
    limit_per_minute: plan.capacity,
    ...(plan.name === 'free'
      ? { upgrade: 'A pro API key raises this limit to 100/minute (try demo key: demo-pro-key).' }
      : {}),
  }),
}), handler);

Alternatives considered: one hardcoded limit per route (what we had - fine for a demo, not a product); a customer database (the honest next step, but heavier than the lesson needs); keying by IP only (cannot distinguish a paying customer from a free one on the same network).

Failure cases, stated: an unknown key fails closed-but-usable (free plan, its own bucket); a pro key shared publicly just drains that key's bucket - isolation by key contains the damage; a missing key header falls back to the caller's IP, the same as before.

Tests (test/plans.test.ts): the registry maps demo keys to plans and unknown keys to free; a free key exhausts at exactly 10 while a pro key continues with limit 100 in its headers; an unknown key gets its own free bucket.

Try it yourself: fire eleven requests at /api/ledger with header "x-api-key: demo-free-key" - the eleventh answers 429 with "plan": "free" and the upgrade hint. Repeat with demo-pro-key and watch X-RateLimit-Limit read 100.

30. Feature upgrade 2: cost-based limiting

What it is, in plain words: before, every request spent exactly one token, as if a cheap lookup and an expensive report cost the same. Now a route can declare what a call actually costs: /api/heavy spends 3 of your 10 tokens per call, so you get three calls, then wait.

Why this is more than a basic limiter: counting requests protects against floods; measuring cost protects the actual resource - CPU seconds, database time, money. This is how real quotas work (an API that charges 1 credit per lookup and 50 per report). Quotas stop being a headcount and become economics.

The mechanism: the change threads one optional number through the whole stack. The RateLimiter interface became consume(key, cost = 1); the pure decision math spends cost tokens and refuses impossible costs up front; the middleware passes the route's cost; the Durable Object validates and applies the same math in shared storage: 

if (tokens >= cost) {
  const afterSpend = tokens - cost;
  ... // allowed: spend the tokens
}
const secondsToWait = (cost - tokens) / refillPerSecond; // rejected: wait for the missing tokens

The guard worth noticing: assertValidCost throws when cost exceeds capacity, because such a request could NEVER be allowed - the bucket can never hold that much. Silently denying forever would look like a bug; a loud config error is the honest behavior. The test suite pins this.

Alternatives considered: separate buckets per route cost (multiplies state for no insight); charging after the work is done (the resource is already spent - too late). Charging at the gate, in tokens, is the whole point.

Failure cases: a zero or negative cost is rejected as a config error; a cost between 1 and capacity just waits longer (retry-after is the time to earn the MISSING tokens, not a fixed penalty).

Tests (test/tokenBucket.test.ts, test/middleware.test.ts): spending 3 of 10 leaves 7; a 3-cost request against 1 remaining token is rejected with a 2-second retry-after (the time to earn 2 more at 1/sec); cost above capacity throws; the middleware header reflects the cost.

Try it yourself: three calls to /api/heavy pass, the fourth waits 12 seconds - the same refill math from section 14, spent in batches of 3.

31. Feature upgrade 3: escalating penalties (jail)

What it is, in plain words: a plain limit treats your first violation and your hundredth the same - wait a few seconds, try again. For a login route that is an invitation: password spraying works precisely because each guess is nearly free. Jail changes the economics: every rejection doubles the next block (30 seconds, then 60, then 120, capped at 30 minutes).

Why this is more than a basic limiter: it turns flood protection into an anti-abuse POLICY with a memory. A real user who fumbles one password waits seconds and is forgiven completely on success - the record clears. An attacker running ten thousand guesses pays exponentially for each one. Security features you can explain as mechanism, not labels, are exactly what interviewers probe for.

The mechanism: the escalation math is one pure function (src/core/jail.ts), shared by the local wrapper and the shared store, the same philosophy as the bucket math: 

export function nextPenalty(prev: PenaltyState | undefined, nowMs: number): PenaltyState {
  const violations = (prev?.violations ?? 0) + 1;
  const blockSeconds = Math.min(JAIL_MAX_SECONDS, JAIL_BASE_SECONDS * 2 ** (violations - 1));
  return { violations, blockedUntilMs: nowMs + blockSeconds * 1000 };
}

Where the jail records live is the important decision: in the Durable Object's storage, not local memory. A jail that exists only per-isolate is one an attacker escapes by landing on the next copy of the worker. A success deletes the record (forgiveness), and idle records are evicted with the same 10-minute policy as buckets (bounded memory). Honest limit, stated in the code: there is no gradual decay of the violation count short of a success or eviction.

A subtlety the test suite pinned: retry-after is the MAX of the bucket's own wait and the jail block. Jail raises the floor; it never shortens a longer bucket wait. (The first version of the test expected jail to dominate a 1-hour bucket wait - the math said otherwise, and the test was wrong, not the code. Same lesson as the reset-time bug in section 7: write the assertion from the math.)

Alternatives considered: permanent bans (one fumble locks a real user forever - unacceptable); IP bans (shared networks punish the innocent); a fixed long block (attackers just wait it out; exponential growth is what changes THEIR economics).

Tests (test/jail.test.ts): the escalation doubles and caps at 30 minutes; an active block refuses without touching the bucket; a success resets the count to zero; the shared-store jail survives object eviction; non-jail routes ignore penalty records entirely.

Try it yourself: six wrong logins against /api/login with the same username - the sixth waits 30 seconds, not 12. A different username is completely unaffected.

32. Feature upgrade 4: the live concurrency proof

What it is, in plain words: click "Run the proof" on the dashboard. Twenty requests fire at the same instant at a fresh bucket of 10 tokens. Exactly 10 pass. Every time. The endpoint exists so the shared store's central claim - atomic check-and-spend - is something anyone can rerun, not a sentence you have to believe.

Why this is more than a basic limiter: the hard part of rate limiting across many servers is the race - two requests both read "1 token left" and both spend it. Section 21 explained why a Durable Object closes that race (single-threaded; Cloudflare's input gates serialize storage-touching work - the platform's own documentation shows the exact read-then-write pattern as safe). This upgrade turns that documented guarantee into a live demonstration. The honest scope, stated in the docs and in the endpoint's own response: the run DEMONSTRATES the behaviour on a bounded burst; the guarantee itself comes from the platform's semantics and is pinned by the test suite. Demonstrating is not proving - and saying so is part of the engineering.

The mechanism: fire N parallel consumes, count the allows (src/demo/proof.ts): 

const results = await Promise.all(Array.from({ length: n }, consumeOne));
const allowed = results.filter((r) => r.allowed).length;
return { requested: n, limit: k, allowed, rejected: n - allowed, passed: allowed === k };

The safety design matters as much as the proof, because a public demo defends itself: every run uses a fresh throwaway probe key (crypto.randomUUID) so it can never touch a real caller's bucket; the burst is fixed and small (20 requests, limit 10); refill is set to roughly zero during the burst so clock noise cannot blur the count; and the endpoint rate-limits ITSELF to 10 runs per minute per visitor - enforced through the same shared store, of course. Twenty requests against the free tier's 100,000-requests-per-day allowance is negligible, which was verified against Cloudflare's published limits before this shipped.

Alternatives considered: a load-test script you run from your laptop (proves nothing about the deployed shared store, and looks like an attack from one IP); a permanent always-on stress bucket (noise in the stats feed); trusting the documentation without a demonstration (the failure mode of every "it scales" claim).

Tests (test/proof.test.ts): exactly K of N on a local bucket; exactly K of N through the shared store with the input-gate behavior modeled as a queue (storage-touching events serialized - the unit test models the guarantee, the live endpoint demonstrates the real thing); the proof endpoint returns 429 after 10 runs in a minute.

33. Scaling, honestly: what breaks first, and the documented path past it

Why this section exists: a mentor asked the right question - how would this handle lakhs of users? The honest answer splits "users" from "requests". A registered-user count alone says nothing about load; what matters is requests per second and requests per day. Two very different workloads can both be called "a lakh of users": occasional demo clicks, or a hundred API calls per user per day (about ten million requests a day). The second hits the account's free-tier cap long before any code-level limit.

The first ceiling is the plan, not the design. On Workers Free, a worker is allowed 100,000 requests per day (Cloudflare Workers limits: https://developers.cloudflare.com/workers/platform/limits/ - read 12 Nov 2026; this is plan-dependent and paid plans raise it). Ten million requests a day is a hundred times that. So "handling lakhs of users" on the current free plan is ruled out by quota before architecture even enters the discussion.

The architectural ceiling, as actually built: every rate-limit decision - every route, plan and caller, plus the concurrency-proof endpoint - goes through ONE Durable Object instance (idFromName('global') in src/worker.ts). That single-threaded object is exactly what makes check-and-spend atomic; the guarantee the concurrency proof demonstrates comes from requests serializing through it. Cloudflare's Durable Objects limits page (https://developers.cloudflare.com/durable-objects/platform/limits/ - read 12 Nov 2026) gives an individual object a SOFT LIMIT of 1,000 requests per second, after which it queues and then returns overload errors. These are published ceilings, not benchmarks of this project: no sustained-load test was run, so the real ceiling of this build is unknown and is stated here as unknown. Two things in this build would pull it below the published number: each decision performs several storage operations (a bucket put, plus a stats get+put for the dashboard feed on every request; jail routes add a penalty read and sometimes a write), and the once-a-minute prune and the stats snapshot use list() over storage, which Cloudflare notes reduces throughput.

Memory is bounded by policy, and that policy is pinned by the test suite - separately from the concurrency demo: the 10,000-key cache cap and the 10-minute idle eviction of buckets and jail records are asserted in the MemoryStore and Durable Object unit tests. What has NOT been measured: CPU time per decision and storage latency under sustained load. So this doc does not claim either is or is not a bottleneck; it claims only that storage size is bounded by the policies above.

The documented scale path - a proposal, not built: Cloudflare's answer is horizontal sharding, and a namespace allows unlimited objects. Sharding this build would mean replacing the single idFromName('global') with a per-limiter or per-caller-hash id, AND rerouting everything that touches the shared object today: the consume calls, the concurrency-proof endpoint, the stats feed and its snapshot, and the prune pass. Per-key atomicity survives because one caller key would always map to one object. But a genuinely hot key still lives in exactly one object, so sharding does not rescue a single hot key - that case needs a different design (for example splitting the budget across objects up front, at the cost of exactness). The global stats view would need its own object or per-shard feeds, and cross-shard totals stop being free. None of this is implemented. The current design is the single shared object, chosen deliberately because it makes the atomicity lesson possible at demo scale.

Beyond this project: multi-region stores, or Cloudflare's native rate-limiting rules for coarse edge protection, are product territory and out of scope here.
