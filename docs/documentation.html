API Rate Limiter - Project Documentation

Mentor project 2 of 2. Owner: Shubhra Jyothsna. Started 9 Nov 2026. This document explains what is built, how it works, and why every tool in it was chosen over the alternatives. It grows as the project grows.

1. What this project is

Shubhra's mentor assigned seven system-design problems and asked for two of them to be built properly, well enough to explain in an interview. This is the second: an API rate limiter - the part of a server that enforces "you may call me 100 times a minute; call 101 waits or fails with HTTP 429 Too Many Requests". The other project (URL shortener) is documented separately.

Everything in sections marked "mentor's ask" comes from his assignment. Design choices, the demo dashboard, and all personal twists are ours, and are labelled as such. Nothing here is copied from a tutorial; every file was written for this project and is explained below.

2. What exists today (9 Nov 2026, ~2:40 AM IST)

A working rate limiter - tested, pushed to GitHub, deployed live, and enforcing shared limits across every copy of the deployment:

  • Three rate-limiting algorithms written from scratch in TypeScript: token bucket, fixed window, sliding window.
  • An Express middleware that puts any route behind a limit, adds standard rate-limit headers, and rejects floods with a proper 429 response.
  • A demo API with three routes limited three different ways, to show limiting is per-route policy.
  • A live dark dashboard that charts allowed vs rejected requests per second, with buttons to fire single requests, bursts and floods.
  • A shared store (Cloudflare Durable Objects) so the limits hold across every copy of the deployed worker; locally the same routes use in-memory state.
  • 20 automated tests, all passing, covering the behaviour an interviewer asks about - including the shared store.

Honest status: every claim above is covered by a test or a live browser check. The GitHub repository is private (Shubhra's choice; it can go public when she says ready) and holds all milestone commits. The demo is live at https://api-rate-limiter.2wf0w2.workers.dev.

4. How the system works

The request flow, end to end:

  1. A request arrives at the Express server (for example POST /api/login).
  2. Before any route logic runs, it passes through the rate-limit middleware. "Middleware" just means code that runs in the middle, before the handler.
  3. The middleware decides WHO is calling - the key. Reads are keyed by IP address; login is keyed by IP plus username (an attacker guessing passwords has no account yet, so keying by user id would not slow them); the heavy route is keyed by API key.
  4. The middleware asks the token bucket: does this key have a token? Locally the bucket lives in memory; on the live deployment the middleware asks the Durable Object, which runs the exact same decision math against the shared buckets. The bucket refills at a steady rate; each request spends one token.
  5. Allowed: the request continues to the real route handler, with X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset headers attached so honest clients can pace themselves.
  6. Rejected: the middleware answers 429 immediately with a Retry-After header and a small JSON body. The route handler never runs, the database is never touched - the flood stops at the gate.
  7. Every decision is recorded (locally by the stats recorder; deployed, inside the Durable Object), and the dashboard page polls the stats feed once a second to draw the live allowed-vs-rejected chart.

5. The three algorithms, and why token bucket won

Fixed window (src/core/fixedWindow.ts) counts requests per clock minute. Simple, but a burst at 10:00:59 and another at 10:01:00 fall in different windows, so twice the limit passes in two seconds. One of the tests proves this with 120 requests accepted under a 60/minute limit. It stays in the project as the baseline to compare against - being able to show its weakness with a test is exactly what an interviewer wants to hear.

Sliding window log (src/core/slidingWindow.ts) remembers the timestamp of every recent request and counts them. Accurate, no edge bursts - but memory grows with traffic per caller. Fine at small scale, expensive at large scale.

Token bucket (src/core/tokenBucket.ts) gives each caller a bucket holding up to N tokens, refilling at a steady rate. Each request spends one token; empty means wait. It allows short bursts while capping the long-term average, uses two numbers of memory per caller, and handles bursts and steady rate with a single mechanism - which is why it protects the demo routes. The decision math is one pure function (consumeToken), so the local limiter and the Durable Object run the identical, test-covered code.

Two details worth noticing in the code: the clock is injected as a parameter, so tests can simulate minutes passing in milliseconds; and a backwards clock jump (a server time correction) is clamped to zero, so time travel can never mint free tokens. Both are test-covered.

6. Known limits, honestly

  • Local in-memory state forgets everything on restart and is invisible to other processes. That is why the deployed worker uses the shared store; npm run dev keeps memory because it is one process.
  • The shared store routes every decision through one named Durable Object. That is what makes each check-and-spend atomic, but it also makes the object the single decision point - the same shape of tradeoff as a single Redis primary. For a demo this is the right call; high-traffic systems shard by key.
  • Keying by IP is imperfect: many users share a NAT/campus IP, and attackers rotate IPs. Real systems layer keys (IP + account + API key), which the middleware supports through its keyGenerator.
  • The stats feed keeps only the last two minutes - it is a teaching instrument, not monitoring.
  • Everything is bounded so the public demo cannot eat itself: at most 10,000 buckets per store, idle keys evicted after 10 minutes, demo buttons fire at most 150 requests in batches of 10.

8. How to run it

npm install, then npm test to see the 20 tests, then npm run dev and open http://localhost:8787 for the dashboard. The deployed version is at https://api-rate-limiter.2wf0w2.workers.dev. The README in the repository repeats this with the API contract.

9. The interview answer this project buys

"Design a rate limiter" - walk through: who is limited (user, IP, API key - and why login limits key on IP plus username), which algorithm (token bucket, and why it beats fixed window - with the edge-burst test as proof), where state lives (memory for one server, a shared store when many share limits - Durable Objects on Cloudflare, Redis on self-hosted, with the store interface making either swap a one-file change), what the response looks like (429 with Retry-After and X-RateLimit headers), and how it is tested (at-limit, refill, isolation, burst, clock safety, shared-store semantics). Each of those sentences has working code and a passing test behind it in this repository.
